## 1. WPA Key Hierarchy

WPA uses a layered key derivation model. The passphrase you type is never used directly — it goes through multiple transformations:

```
Passphrase (human-readable)
    │
    ▼
  PMK  ← Pairwise Master Key (256-bit, derived once per SSID)
    │
    ▼
  PTK  ← Pairwise Transient Key (per-session, per-connection)
    │
    ├── KCK (Key Confirmation Key)    — verifies handshake integrity
    ├── KEK (Key Encryption Key)      — encrypts GTK delivery
    └── TK  (Temporal Key)            — encrypts actual WiFi data frames
```

### Key Lifetimes

| Key | Lifetime | Scope |
|-----|----------|-------|
| **PSK** | Until user changes passphrase | Per-SSID |
| **PMK** | Until PMKSA expires (~12 hours) or PSK changes | Per AP-STA pair |
| **PTK** | Until disconnect or rekey | Per session |
| **GTK** | Until AP rotates it (~1-24 hours) | Per BSS (shared by all clients) |

---

## 2. PSK to PMK Derivation

### WPA2-PSK

For WPA2-PSK, the PMK is derived using PBKDF2:

$$PMK = PBKDF2(SHA1, \text{Passphrase}, \text{SSID}, 4096, 256)$$

- **Input**: Passphrase (8-63 ASCII chars) + SSID (network name)
- **Output**: 256-bit (32 bytes) PMK
- **Iterations**: 4096 rounds of HMAC-SHA1
- **Deterministic**: Same passphrase + same SSID = same PMK every time

### WPA3-SAE

For SAE (Simultaneous Authentication of Equals), PMK derivation is fundamentally different:

$$PMK = SAE\text{-}Commit\text{-}Confirm(Password, MAC_{AP}, MAC_{STA})$$

- Uses Dragonfly key exchange (elliptic curve)
- PMK is **unique per session** even with the same password
- Password correctness is verified **during authentication** (before association)
- Resistant to offline dictionary attacks

---

## 3. PMK to PTK Derivation

The PTK is derived fresh for every new connection:

$$PTK = PRF\text{-}384(PMK, \text{"Pairwise key expansion"}, Min(AA,SPA) \| Max(AA,SPA) \| Min(ANonce,SNonce) \| Max(ANonce,SNonce))$$

Where:
- **PMK** = Pairwise Master Key (32 bytes)
- **AA** = Authenticator Address (AP's MAC address)
- **SPA** = Supplicant Address (Client's MAC address)
- **ANonce** = AP's random nonce (32 bytes, sent in M1)
- **SNonce** = Client's random nonce (32 bytes, generated by client)
- **PRF-384** = Pseudo-Random Function producing 384 bits (48 bytes)

### Why PTK Is Unique Per Session

Even if PMK stays the same (same passphrase, same SSID):
- ANonce = random (new every connection, generated by AP)
- SNonce = random (new every connection, generated by client)
- → PTK is different every single time

This ensures **forward secrecy per session** — capturing one session's PTK doesn't help decrypt others.

---

## 4. PTK Components — KCK, KEK, TK

The 48-byte PTK (for CCMP) is split into three sub-keys:

```
PTK (48 bytes)
├── Bytes  0-15: KCK (Key Confirmation Key)  — 128 bits
├── Bytes 16-31: KEK (Key Encryption Key)    — 128 bits
└── Bytes 32-47: TK  (Temporal Key)          — 128 bits
```

| Sub-Key | Size | Purpose | Used In |
|---------|------|---------|---------|
| **KCK** | 16 bytes | Compute MIC (Message Integrity Check) on EAPOL frames | M2, M3, M4 — proves both sides have the same PMK |
| **KEK** | 16 bytes | Encrypt/decrypt key data in EAPOL frames | M3 — AP encrypts GTK with KEK before sending |
| **TK** | 16 bytes | Encrypt/decrypt actual WiFi data frames (AES-CCMP) | All data frames after handshake completes |

### MIC (Message Integrity Check)

$$MIC = HMAC\text{-}SHA1\text{-}128(KCK, \text{EAPOL Frame})$$

The MIC is how both sides verify they derived the **same PTK** (and therefore have the **same PMK** and **same PSK**). If the PSK is wrong → PMK is wrong → PTK is wrong → KCK is wrong → MIC doesn't match → **handshake fails**.

## 5. The 4-Way Handshake (EAPOL)

The 4-way handshake establishes the PTK and delivers the GTK. It occurs after authentication and association.

```
        AP (Authenticator)                         STA (Supplicant/Client)
              │                                           │
              │  ┌─────────────────────────────────┐      │
              │  │ AP already has: PMK, generates   │      │
              │  │ ANonce (random 32 bytes)         │      │
              │  └─────────────────────────────────┘      │
              │                                           │
    M1        │──── ANonce [+ optional PMKID] ──────────► │
              │                                           │  Client derives:
              │                                           │  PMK (from PSK+SSID)
              │                                           │  PTK (from PMK+nonces+MACs)
              │                                           │  Generates SNonce
              │                                           │
    M2        │◄──── SNonce + MIC + RSN IE ──────────────│
              │                                           │
              │  AP derives same PTK                      │
              │  AP verifies MIC from M2                  │
              │  (if MIC wrong → AP silently drops M2)    │
              │                                           │
    M3        │──── ANonce + MIC + Encrypted GTK ───────►│
              │                                           │
              │                                           │  Client verifies MIC from M3
              │                                           │  Client decrypts GTK with KEK
              │                                           │  Client installs PTK + GTK
              │                                           │
    M4        │◄──── MIC (acknowledgment) ───────────────│
              │                                           │
              │  AP installs PTK                          │
              │  ═══════════════════════════════════       │
              │       Encrypted data begins                │
              │  ═══════════════════════════════════       │
```

### What Each Message Carries

| Message | Direction | Key Content | Purpose |
|---------|-----------|-------------|---------|
| **M1** | AP → STA | ANonce, optional PMKID | "Here's my nonce, derive the PTK" |
| **M2** | STA → AP | SNonce, MIC, RSN IE | "Here's my nonce + proof I know the PSK" |
| **M3** | AP → STA | ANonce, MIC, encrypted GTK | "Confirmed. Here's the group key" |
| **M4** | STA → AP | MIC | "Got it. Ready to encrypt" |

### Timing

A normal 4-way handshake completes in **5-20 ms** over WiFi. It is not a computationally expensive operation.

## 6. Why the 4-Way Handshake Fails

### Failure Mode: WRONG_KEY

```
STA has PSK_old → derives PMK_old → derives PTK_old → computes MIC_old
AP  has PSK_new → derives PMK_new → derives PTK_new → expects MIC_new

STA sends M2 with MIC_old
AP receives M2, computes MIC_new, compares:
  MIC_old ≠ MIC_new → DROP M2 (silently)

AP retries M1 → same result → eventually:
  "4-Way Handshake failed - pre-shared key may be incorrect"
```

**Key insight**: The AP doesn't send a "wrong password" message. It **silently drops M2** and retries M1. After several retries (typically 4), the handshake times out with `WRONG_KEY`.

### Failure Mode: Timeout

```
STA sends M2 → AP never responds (AP crashed, deauthed, out of range)
STA waits ~2 seconds → CTRL-EVENT-4WAY-HANDSHAKE-TIMEOUT
```

### All Failure Causes

| Cause | Log Message | Mechanism |
|-------|------------|-----------|
| **Wrong PSK** | `pre-shared key may be incorrect` | MIC mismatch in M2 |
| **Timeout** | `4WAY-HANDSHAKE-TIMEOUT` | No M3 received within timeout |
| **RSN IE mismatch** | `IE in 3/4 msg does not match` | AP changed security params mid-handshake |
| **Replay attack** | `EAPOL-Key Replay Counter did not increase` | Stale/replayed M1 or M3 |
| **Association rejected** | `ASSOC-REJECT` | Happens before handshake even starts |

## 7. PMKSA Cache

### What Is PMKSA?

**PMKSA** = Pairwise Master Key Security Association

It's a cache that stores:
- PMK (32 bytes)
- PMKID (16 bytes)
- AP MAC address (AA)
- Expiration time

### Purpose

Skip PMK derivation on reconnect. Instead of re-deriving PMK from PSK (or worse, re-doing full EAP authentication), the client reuses the cached PMK.

### How It's Created

```
1. Client connects to AP
2. AP sends M1 with PMKID
3. Client derives PMK, stores: {PMKID, PMK, AP_MAC, expiry} → PMKSA cache
4. Later, client reconnects to same AP
5. AP sends M1 with same PMKID
6. Client finds match in cache → uses cached PMK (no re-derivation)
```

### Creation Timing

PMKSA cache creation takes **< 0.1 ms** — it's just saving 32 bytes to RAM. It is not a computation bottleneck and **cannot cause handshake timeout**.

### Expiration

- Default: **43200 seconds (12 hours)**
- Configurable via `dot11RSNAConfigPMKLifetime`
- When expired: entry removed, full derivation on next connection

### When PMKSA Caching Matters

| Auth Type | PMKSA Value | Why |
|-----------|-------------|-----|
| **802.1X/EAP** | **Critical** | Avoids full RADIUS round-trip (2-5 sec saved) |
| **SAE (WPA3)** | **Useful** | Avoids SAE commit/confirm exchange |
| **WPA2-PSK** | **Minimal** | PMK always re-derivable from PSK (~0.01ms) |

### Important: PMKSA Cache Does NOT Prevent Handshake Failure

PMKSA is about **speed**, not **correctness**:

```
Correct PSK  → handshake succeeds (with or without PMKSA cache)
Wrong PSK    → handshake fails    (with or without PMKSA cache)
```

If PSK changes while PMKSA cache still has the old PMK, the cached PMK becomes **stale** — the handshake will fail with WRONG_KEY because the MIC computed from the old PMK won't match what the AP expects.

## 8. PMKID — Pairwise Master Key Identifier

### What Is PMKID?

A **16-byte hash** that uniquely identifies a specific PMK. It lets both AP and STA agree on which cached PMK to use.

### How It's Calculated

$$PMKID = HMAC\text{-}SHA1\text{-}128(PMK, \text{"PMK Name"} \| AA \| SPA)$$

Where:
- **PMK** = Pairwise Master Key (32 bytes)
- **"PMK Name"** = literal ASCII string
- **AA** = Authenticator Address (AP MAC, 6 bytes)
- **SPA** = Supplicant Address (Client MAC, 6 bytes)
- Output: first 16 bytes of HMAC-SHA1

### Where PMKID Appears

PMKID is sent by the AP in **EAPOL M1** inside the key data field:

```
M1 with PMKID:    key data - hexdump(len=20):  dd 0e 00 0f ac 04 [16-byte PMKID]
M1 without PMKID: key data - hexdump(len=0)    ← AP chose not to send it
```

### Who Decides to Send PMKID?

**The AP decides.** The client cannot request or create PMKID on its own. Many home APs (especially for WPA2-PSK) don't send PMKID because:
- For PSK, PMK is always re-derivable from the passphrase
- The performance gain is negligible (~0.01ms)
- It's an optional optimization, not a requirement

### PMKID Flow

```
AP sends M1:
  ├─ PMKID present?
  │   ├─ YES → Client checks cache for matching PMKID
  │   │   ├─ FOUND  → Use cached PMK (fast path)
  │   │   └─ MISS   → Derive PMK from PSK (normal path)
  │   └─ Client stores {PMKID, PMK} in PMKSA cache
  └─ PMKID absent?
      └─ Derive PMK from PSK (normal path), no caching
```

## 9. SAE (WPA3) vs WPA2-PSK

### Authentication Flow Comparison

```
WPA2-PSK:
  Open Auth → Association → 4-Way Handshake
  └── Password verified HERE (MIC in M2)
  └── If wrong PSK: handshake fails silently

SAE (WPA3):
  SAE Commit → SAE Confirm → Association → 4-Way Handshake
  └── Password verified HERE (during SAE frames)
  └── If wrong password: auth fails BEFORE association
```

### Key Differences

| Feature | WPA2-PSK | SAE (WPA3) |
|---------|----------|------------|
| Password verification | During 4-way handshake (M2) | During SAE auth frames |
| Offline dictionary attack | Vulnerable (capture M1+M2, brute-force offline) | Resistant (Dragonfly exchange) |
| PMK derivation | Deterministic: `PBKDF2(PSK, SSID)` | Unique per session (Dragonfly) |
| Forward secrecy | No (same PMK if same PSK) | Yes (different PMK each time) |
| PMKSA caching | Common | Optional (AP must support) |
| Auth failure message | `WRONG_KEY` (after handshake) | `ASSOC-REJECT` or `SAE auth failed` (before handshake) |

### Transitional Mode (WPA2/WPA3)

Many APs support both simultaneously:

```
key_mgmt=WPA-PSK SAE WPA-PSK-SHA256 SAE
```

The client and AP negotiate which one to use:
- If both support SAE → use SAE
- If client only supports WPA-PSK → fallback to WPA2-PSK

## 10. GTK — Group Temporal Key

### What Is GTK?

The **Group Temporal Key** encrypts broadcast/multicast frames. Unlike PTK (unique per client), GTK is **shared by all clients** on the same BSS.

### Delivery

GTK is delivered encrypted inside M3 of the 4-way handshake:

```
AP encrypts GTK with client's KEK → sends in M3
Client decrypts GTK with KEK → installs for broadcast reception
```

### Rotation

The AP periodically rotates GTK (Group Key Handshake):

```
AP → STA: Group M1 (new encrypted GTK + MIC)
STA → AP: Group M2 (acknowledgment + MIC)
```

This is a **2-way handshake** (not 4-way), using the existing PTK's KCK and KEK.

## 11. wpa_supplicant & wpa_cli Reference

### Architecture

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────┐
│   wpa_cli        │────►│  wpa_supplicant   │────►│  Driver  │──── WiFi Radio
│ (control tool)   │◄────│  (daemon)         │◄────│ (nl80211)│
└─────────────────┘     └──────────────────┘     └─────────┘
        │                        │
   ctrl_interface           Config file:
   (Unix socket)         wpa_supplicant.conf
```

### Key wpa_cli Commands

#### Connection Management

```bash
wpa_cli -i wlan0 status              # Current connection state
wpa_cli -i wlan0 scan                # Trigger scan
wpa_cli -i wlan0 scan_results        # Show scan results
wpa_cli -i wlan0 list_networks       # List configured networks
wpa_cli -i wlan0 select_network 0    # Connect to network ID 0
wpa_cli -i wlan0 disconnect          # Disconnect
wpa_cli -i wlan0 reconnect           # Reconnect (if disconnected)
wpa_cli -i wlan0 reassociate         # Force re-association (even if connected)
```

#### Network Configuration

```bash
wpa_cli -i wlan0 add_network                        # Add new network (returns ID)
wpa_cli -i wlan0 set_network 0 ssid '"MyNetwork"'   # Set SSID
wpa_cli -i wlan0 set_network 0 psk '"MyPassword"'   # Set PSK
wpa_cli -i wlan0 set_network 0 key_mgmt "WPA-PSK"   # Set auth type
wpa_cli -i wlan0 enable_network 0                    # Enable network
wpa_cli -i wlan0 save_config                         # Write to disk
```

#### PMKSA Cache

```bash
wpa_cli -i wlan0 pmksa           # List PMKSA cache entries
wpa_cli -i wlan0 pmksa_flush     # Clear all PMKSA cache entries
```

> **Note**: `pmksa_get` and `pmksa_set` require wpa_supplicant **2.10+**. Version 2.9 only has `pmksa` and `pmksa_flush`.

#### Debugging

```bash
wpa_cli -i wlan0 log_level DEBUG   # Enable verbose debug output
wpa_cli -i wlan0 log_level INFO    # Restore normal logging
```

### Configuration File (wpa_supplicant.conf)

```ini
ctrl_interface=/var/run/wpa_supplicant
update_config=1          # Allow wpa_cli save_config to write this file
country=US
pmf=1                    # Protected Management Frames (required for WPA3)

network={
    ssid="NetworkName"
    psk="Passphrase"
    key_mgmt=WPA-PSK SAE WPA-PSK-SHA256 SAE
}
```

### `set_network` vs Editing Config File

| Method | Changes Runtime? | Persists Reboot? |
|--------|:---:|:---:|
| `set_network` only | ✅ | ❌ |
| `set_network` + `save_config` | ✅ | ✅ |
| Edit conf file + restart wpa_supplicant | ✅ (after restart) | ✅ |

**Best practice**: Use `wpa_cli set_network` + `save_config`. Safer than editing the file directly.

## 12. PMKSA Cache Management via wpa_cli

### Viewing PMKSA Cache

```bash
wpa_cli -i wlan0 pmksa
```

Output when cache has entries:
```
Index / AA / PMKID / expiration (in seconds) / opportunistic
1 / aa:bb:cc:dd:ee:ff / 0123456789abcdef0123456789abcdef / 43100 / 0
```

Output when empty:
```
Index / AA / PMKID / expiration (in seconds) / opportunistic
```

### Why PMKSA Cache Might Be Empty

| Reason | Explanation |
|--------|-------------|
| AP didn't send PMKID in M1 | AP chose not to enable PMKSA caching |
| SAE connection | SAE PMKSA may be stored separately (not shown by `pmksa`) |
| Cache expired | Default 12-hour lifetime elapsed |
| `pmksa_flush` was called | Cache explicitly cleared |
| Fresh boot | PMKSA cache is in RAM only, lost on reboot |

### Can You Manually Create PMKSA?

**No.** PMKID is derived from both AP and client inputs:

$$PMKID = HMAC(PMK, \text{"PMK Name"} \| AP_{MAC} \| Client_{MAC})$$

Both sides must agree. The client cannot unilaterally inject a valid PMKSA entry (unless using `pmksa_set` in wpa_supplicant 2.10+ with a previously exported entry from `pmksa_get`).

## 13. RDK WiFi Recovery Framework

RDK-based devices (cameras, STBs) have an automatic WiFi recovery mechanism managed by DEVICECTL/NETSRVMGR:

### Recovery Timeline

```
0s     — Connection lost detected
         │
60s    — Tier 1: wpa_supplicant reset
         │  Action: restart wpa_supplicant, retry with stored credentials
         │
120s   — Tier 2: WiFi driver reset  
         │  Action: unload/reload WiFi kernel module, restart wpa_supplicant
         │
180s+  — Tier 3: LNF (Lost and Found) recovery
         │  Action: connect to hidden LNF SSID via EAP-TLS
         │  Fetch correct credentials from cloud
         │
~600s  — Tier 4: Watchdog reboot
           Action: full device reboot
```

### Important Behavior

- Recovery runs **automatically** — you cannot easily test wpa_cli PSK changes without the recovery framework overriding your changes
- `set_network` changes may be **reverted** by NETSRVMGR within 60 seconds
- To test handshake failures manually, you may need to stop the recovery service first

## 14. LNF (Lost and Found) Recovery

### What Is LNF?

A cloud-based credential recovery mechanism for RDK devices. When a device can't connect to its configured network, it falls back to a special hidden SSID to fetch new credentials.

### How It Works

```
Camera can't connect to home WiFi
    │
    ▼
Scans for LNF SSID (hidden, broadcast by gateway)
    │
    ▼
Connects via EAP-TLS (802.1X with client certificate)
    │  - No PSK needed
    │  - Uses device's factory-provisioned certificate
    │
    ▼
Establishes tunnel to cloud server
    │  (e.g., tvxlanf-c3-c00001-b.ch.tvx.comcast.com)
    │
    ▼
Sends HTTP request for credentials
    │
    ▼
Cloud responds with current SSID + PSK
    │  (HTTP 200, "Credentials changed: SSID or KeyPassphrase")
    │
    ▼
Camera stores new credentials and connects to home WiFi
```

### Why LNF Exists

If a user changes their WiFi password, all connected devices get disconnected. Smart devices (cameras, sensors) have no UI to enter the new password. LNF solves this by providing a **secure out-of-band channel** to retrieve updated credentials automatically.

## 15. Common Misconceptions

### Misconception 1: "PMKSA cache prevents handshake failure"

**Wrong.** PMKSA cache is an optimization for speed, not correctness. If the PSK changed, the cached PMK is stale — the handshake will fail regardless.

### Misconception 2: "PMKSA cache creation takes time and causes timeout"

**Wrong.** PMKSA creation is saving 32 bytes to RAM — takes microseconds. A handshake timeout means the AP didn't respond, not that the client was slow.

### Misconception 3: "The client creates PMKSA cache on its own"

**Wrong.** PMKSA cache requires the AP to send PMKID in M1. If the AP doesn't send it, there's nothing to cache. It's an **AP-side decision**.

### Misconception 4: "WPA2-PSK needs PMKSA caching"

**Not really.** For PSK, the PMK is always `PBKDF2(passphrase, SSID)` — re-derivable instantly. PMKSA caching is critical for 802.1X/EAP where re-authentication involves a RADIUS server.

### Misconception 5: "Empty PMKSA means something is broken"

**Wrong.** Many home APs don't send PMKID for WPA2-PSK. Empty PMKSA is normal. The 4-way handshake works fine without it — it just does full derivation each time.

### Misconception 6: "SAE and WPA2-PSK fail the same way"

**Wrong.** WPA2-PSK fails **during the 4-way handshake** (MIC mismatch in M2). SAE fails **during authentication frames** (before association even happens). The error messages and timing are different.

## Quick Reference Cheat Sheet

### Key Derivation Chain

```
Passphrase + SSID ──PBKDF2──► PMK ──PRF──► PTK ──split──► KCK + KEK + TK
                                                              │     │     │
                                                         MIC check  │  Data encryption
                                                              GTK delivery
```

### 4-Way Handshake One-liner

```
M1(ANonce) → M2(SNonce+MIC) → M3(MIC+GTK) → M4(MIC) → CONNECTED
```

### Failure Quick Diagnosis

```
"pre-shared key may be incorrect"  →  PSK mismatch (most common)
"4WAY-HANDSHAKE-TIMEOUT"           →  AP not responding
"ASSOC-REJECT"                     →  Rejected before handshake
"IE in 3/4 msg does not match"     →  Security parameter mismatch
```
